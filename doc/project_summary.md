# Uzbek Text Simplifier — сводка проекта

Капстоун-проект: сервис, упрощающий сложные узбекские тексты
(юридические документы) для обычного читателя.

## Идея

Выбор пал на **NLP для узбекского языка** — нишу почти без готовых
инструментов (в отличие от английского). Из вариантов (классификация
новостей / тональность / NER / упрощение текста) выбрано **text
simplification** — сильнее по бизнес-ценности и без готовых конкурентов
под узбекский.

**Архитектура:**

1. Сбор parallel-корпуса (сложный ↔ простой текст, домен law)
2. Fine-tuning mT5-small на корпусе
3. Десктоп-приложение на Tkinter

## Сбор корпуса

Юридический корпус собран парсером `uz_yur_parser.py` с сайта lex.uz —
самый "сложный" стилистический полюс узбекского текста. Чанкинг —
100–200 слов по границам предложений.

Сложность текста считается тремя эвристиками (без готовых NLP-инструментов
под узбекский): средняя длина предложения, доля редких слов, средняя длина
слова → взвешенный `complexity_score`.

## Объединение и очистка

- **Итог: 6000+ пар** сложный ↔ упрощённый текст, домен `law`
- **Дедуп решён**: переход с дедупа по `url+chunk_id` на дедуп по
нормализованному тексту чанка — ловит повторы текста, получившие разный
chunk_id в разных прогонах парсера
- Очистка мусора разметки (LaTeX-дампы, HTML-теги, обрывки твит-виджетов,
zero-width символы) выполнена на этапе сбора

## Инструкции для teacher-модели (генерация parallel-пар)

Использована **v2** — агрессивная стратегия: сократить длину на 40–60%,
разрешено убирать даты, номера статей закона, статистику ради простоты.
Выбор сделан осознанно и зафиксирован — весь датасет сгенерирован по
единой инструкции, без методологической неоднородности.

## Обучение

- База: `google/mt5-small`, task-prefix `"simplify: "`
- Данные: `domain_legal.csv` (6000+ пар, только домен `law`)
- Оптимизатор Adafactor, LR 1e-3, 8 эпох, `fp16` выключен (mT5 даёт
NaN loss в half precision)
- Метрики на валидации (эпоха 6/8): ROUGE-L ≈ 0.28, chrF ≈ 44.7,
монотонный рост без плато

### Как читать метрики

Обе метрики сравнивают вывод модели с teacher-generated таргетом (не с
эталоном, проверенным человеком):

- **ROUGE-L** — совпадение слов и порядка. Опубликованных бенчмарков
text simplification для узбекского нет — сравнивать не с чем.
- **chrF** — F-мера по символьным n-граммам, устойчивее к морфологии,
чем BLEU/ROUGE. Важно для узбекского как агглютинативного языка, где
одно слово имеет много словоформ.

Обе метрики — baseline, а не финальное доказательство качества:
показывают близость к teacher-выводу, а не реальную упрощённость или
сохранение смысла. Нужен human-eval.

## Проверка качества

Прогнан через DataStory (Tkinter + Gemini) и ручной аудит. Автоматические
"тревоги" AI-анализа (уникальность `text`, "выбросы" в длине чанков,
будущие даты 2026) — ложные срабатывания, ожидаемые для NLP-датасета.
Ручной аудит дополнительно выявил утечку разметки (LaTeX/HTML/твиттер),
не пойманную парсером и DataStory — исправлено.

## Статус

**Проект полностью готов.** Датасет — 6000+ пар, дедуп решён, модель
обучена, десктоп-приложение на Tkinter работает.

Открытые вопросы перед публикацией:

## Спецификация: планируемые фичи

### 1. Конфигурируемые параметры упрощения

**Цель:** дать пользователю управлять поведением модели вместо
хардкода под инструкцию v2.

| Параметр | Тип | Диапазон / значения | По умолчанию |
|---|---|---|---|
| `aggressiveness` | enum | `conservative` (v1-стиль, 85–95% сохранения) / `balanced` / `aggressive` (v2-стиль, −40–60% длины) | `balanced` |
| `max_length_ratio` | float | 0.3–1.0 (доля от исходной длины) | 0.6 |
| `drop_dates` | bool | true/false | false |
| `drop_law_refs` | bool | true/false (убирать номера статей закона) | false |
| `drop_stats` | bool | true/false | false |

**Хранение:** локальный `config.json` рядом с приложением, читается при
старте, редактируется через окно настроек (Tkinter `Toplevel`).

**Влияние на инференс:** параметры транслируются в task-prefix/промпт
модели (например, `"simplify [aggressiveness=conservative]: "`) —
требует до-обучения модели на данных с размеченным уровнем
агрессивности, либо промпт-инжиниринга без переобучения (fallback на
MVP-версию).

### 2. Упрощение текста с любого места (global hotkey)

**Цель:** выделить текст в любом приложении ОС → нажать сочетание
клавиш → всплывающее окно с упрощённым вариантом.

**Поток:**
1. Фоновый процесс слушает глобальную комбинацию клавиш (например,
`Ctrl+Alt+S`)
2. По нажатию — эмуляция `Ctrl+C` для захвата текущего выделения из
буфера обмена
3. Текст отправляется в модель (локальный инференс или через уже
запущенный процесс приложения)
4. Результат показывается в лёгком всплывающем окне (Tkinter
`Toplevel`, `overrideredirect(True)`, поверх всех окон)

**Технические зависимости:**
- Windows: `keyboard` / `pynput` для глобального хоткея, `pyperclip`
для буфера обмена
- Системный трей: `pystray` — приложение сворачивается в трей и не
занимает панель задач
- Важно проверить конфликт хоткея с другими приложениями и дать
пользователю переназначить комбинацию

**Риски:** задержка инференса на CPU может сделать popup-опыт
некомфортным — нужно тестировать время отклика, возможно кэшировать
модель в памяти между вызовами (держать процесс живым, не
перезапускать инференс с нуля).

### 3. Авто-форматирование в Markdown

**Цель:** по нажатию кнопки преобразовать упрощённый текст в Markdown
со структурой (заголовки, списки, выделение ключевых терминов).

**Поток:**
1. После получения упрощённого текста — кнопка "В Markdown"
2. Постобработка (эвристики или отдельный вызов модели/промпта):
 - разбиение на смысловые блоки → `##` подзаголовки
 - перечисления (условия, права, обязанности) → маркированные списки
 - ключевые юридические термины → **выделение жирным**
3. Результат показывается в текстовом поле с превью (или экспорт в
`.md` файл)

**Технические варианты реализации:**
- **Эвристический** (быстро, без доп. обучения): regex/rule-based —
искать перечисления по маркерам ("во-первых", "также", запятые между
однородными пунктами) и переводить в списки
- **Через LLM-постобработку**: отдельный промпт поверх упрощённого
текста — точнее, но требует доступа к более крупной модели или API

**Открытый вопрос:** нужно решить, делать ли это отдельным лёгким
правило-based модулем (надёжнее, предсказуемее) или LLM-вызовом
(гибче, но добавляет зависимость и время отклика) — стоит вынести на
обсуждение с научруком перед реализацией.
