# SPEC.md — планируемые фичи

Технический спек для трёх фич, запланированных после защиты капстоуна.
Проект в статусе "полностью готов" (6000+ пар, дедуп решён,
Tkinter-приложение работает) — ниже roadmap поверх текущей версии.

---

## 1. Конфигурируемые параметры упрощения

### Проблема
Сейчас поведение модели зашито под инструкцию v2 (агрессивная
стратегия, −40–60% длины). Пользователь не может подстроить упрощение
под свои нужды.

### Параметры

| Параметр | Тип | Диапазон / значения | По умолчанию |
|---|---|---|---|
| `aggressiveness` | enum | `conservative` / `balanced` / `aggressive` | `balanced` |
| `max_length_ratio` | float | 0.3–1.0 (доля от исходной длины) | 0.6 |
| `drop_dates` | bool | true/false | false |
| `drop_law_refs` | bool | true/false (убирать номера статей закона) | false |
| `drop_stats` | bool | true/false | false |

### Хранение
Локальный `config.json` рядом с приложением. Читается при старте,
редактируется через окно настроек (`tkinter.Toplevel`).

```json
{
 "aggressiveness": "balanced",
 "max_length_ratio": 0.6,
 "drop_dates": false,
 "drop_law_refs": false,
 "drop_stats": false
}
```

### Влияние на инференс
Два варианта:
- **Без переобучения (MVP):** параметры транслируются в
promt/task-prefix (`"simplify [aggressiveness=conservative]: "`) —
модель не обучена явно на такой разметке, эффект не гарантирован
- **С переобучением:** датасет размечается уровнем агрессивности
(v1-инструкция → `conservative`, v2 → `aggressive`), модель
дообучается с этим as conditioning — надёжнее, но требует новых данных

**Рекомендация:** начать с MVP (промпт-инжиниринг), измерить, даёт ли
эффект, и только потом решать про доразметку/дообучение.

### UI
Отдельное окно настроек: слайдер для `max_length_ratio`, radio-buttons
для `aggressiveness`, три чекбокса для `drop_*`. Кнопка "Сохранить" →
запись в `config.json`.

## 2. Упрощение с любого места (global hotkey)

### Проблема
Сейчас упрощение работает только внутри приложения — нужно копировать
текст, переключаться в приложение, вставлять. Хочется: выделил текст
где угодно → хоткей → результат.

### Поток

1. Фоновый процесс слушает глобальную комбинацию клавиш (`Ctrl+Alt+S`
по умолчанию, переназначаемо)
2. По нажатию — эмуляция `Ctrl+C` для захвата выделенного текста в
буфер обмена
3. Текст отправляется в модель (используется уже запущенный процесс
приложения — модель держится в памяти, не перезапускается)
4. Результат отображается во всплывающем окне поверх всех окон

### Технические зависимости

| Компонент | Библиотека | Назначение |
|---|---|---|
| Глобальный хоткей | `keyboard` или `pynput` | перехват комбинации вне фокуса приложения |
| Буфер обмена | `pyperclip` | чтение выделенного текста |
| Popup-окно | `tkinter.Toplevel(overrideredirect=True)` | окно без рамки, поверх всех |
| Системный трей | `pystray` | сворачивание приложения, доступ к иконке в трее |

### Псевдокод

```python
import keyboard, pyperclip, time
from tkinter import Toplevel

def on_hotkey():
 keyboard.send("ctrl+c")
 time.sleep(0.1) # дать системе обновить буфер
 text = pyperclip.paste()
 simplified = model.simplify(text) # модель уже в памяти
 show_popup(simplified)

keyboard.add_hotkey("ctrl+alt+s", on_hotkey)
```

### Риски и открытые вопросы
- **Задержка инференса на CPU** — если popup появляется через 3-5 сек,
это плохой UX; нужно измерить и решить, нужен ли индикатор загрузки
- **Конфликт хоткея** с другими приложениями — дать пользователю
переназначить в настройках
- **Race condition с буфером обмена** — `Ctrl+C` асинхронен, нужна
проверка/таймаут, что буфер реально обновился, а не отдаёт старое
значение

## 3. Авто-форматирование в Markdown

### Проблема
Упрощённый текст выдаётся плоским блоком. Хочется кнопку, которая
структурирует его: заголовки, списки, выделение терминов.

### Поток

1. После получения упрощённого текста — кнопка "В Markdown"
2. Постобработка текста (см. варианты ниже)
3. Результат — в текстовом поле с превью или экспорт в `.md`

### Варианты реализации

**A. Эвристический (rule-based)**
- Разбиение на абзацы → смысловые блоки
- Перечисления (маркеры "во-первых", "также", однородные пункты через
запятую) → маркированные списки `- `
- Ключевые юридические термины (частотный словарь из корпуса) →
`**жирный**`
- Плюсы: быстро, предсказуемо, без доп. зависимостей
- Минусы: хрупко на нестандартных формулировках

**B. LLM-постобработка**
- Отдельный промпт поверх уже упрощённого текста: "разбей на структуру
markdown с заголовками и списками"
- Плюсы: гибче, лучше держит смысловую структуру
- Минусы: требует доступа к более крупной модели/API, увеличивает
время отклика и добавляет внешнюю зависимость

### Рекомендация
Начать с варианта A (эвристика) как MVP — не требует новой
инфраструктуры. Вариант B — если качество эвристики окажется
недостаточным, обсудить с научруком целесообразность внешнего API-вызова
(вопрос стоимости/задержки для десктоп-приложения).

### Пример эвристики (упрощённо)

```python
import re

def to_markdown(text: str) -> str:
 # эвристика для перечислений
 text = re.sub(r"(во-первых|во-вторых|также|кроме того)",
        lambda m: f"\n- {m.group(0)}", text, flags=re.IGNORECASE)
 # выделение терминов из частотного словаря
 for term in LEGAL_TERMS:
 text = text.replace(term, f"**{term}**")
 return text
```

## Приоритизация

| Фича | Сложность | Ценность для демо | Порядок |
|---|---|---|---|
| Авто-форматирование (эвристика) | низкая | средняя | 1 |
| Конфигурируемые параметры | средняя | средняя | 2 |
| Global hotkey | высокая (ОС-специфика, race conditions) | высокая (эффектно на защите) | 3 |
